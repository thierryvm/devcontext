Piège Windows résolu le 8 août — deux ssh.exe cohabitent

Git utilise par défaut C:\Program Files\Git\usr\bin\ssh.exe, qui ne sait pas parler à l'agent SSH de Windows. Une clé protégée par phrase secrète échoue donc silencieusement en Permission denied (publickey), alors qu'un ssh -T tapé à la main fonctionne — celui-ci utilise C:\WINDOWS\System32\OpenSSH\ssh.exe.

Correctif appliqué : git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe". À rejouer sur toute machine Windows où une clé porte une phrase secrète.

1 · Le principe : ce qui est deviné, ce qui ne l'est pas

Aucune application ne devine quoi que ce soit. Il n'y a que deux mécanismes, et un seul est automatique.

Automatique — git décide par le chemin du dossier

ctx-new écrit ceci dans ~/.gitconfig :

[includeIf "gitdir/i:F:/PROJECTS/Apps/"]
	path = F:/CTX/perso/gitconfig

git relit ce fichier à chaque commande et choisit l'identité selon l'emplacement du dépôt. Rien à taper, jamais. Ça marche depuis le bouton Source Control de VS Code, depuis un agent IA, depuis n'importe quel terminal. C'est pour ça que Client A a dû sortir de Apps\ : deux racines imbriquées rendaient la règle ambiguë.

Manuel — tout le reste dépend du lancement

Les comptes connectés (GitHub, Vercel, Supabase, Copilot) ne sont pas attachés au dossier. Ils sont attachés :

  • soit au terminal dans lequel tu es → posé par work <contexte>
  • soit à comment l'application a été démarrée → code-ctx, web-ctx
La question que tu as posée : « j'ai ankora ouvert dans VS Code, si je tape work perso dans le terminal, il comprend ? »

Le terminal, oui. Il reçoit les variables du contexte. Attention : work fait aussi un cd vers la racine — tu sortirais d'ankora. Pour rester où tu es : work perso -NoCd.

La fenêtre VS Code, non. Son compte GitHub et son Copilot restent ceux de l'instance globale. Un terminal intégré ne peut pas reconfigurer l'éditeur qui l'héberge. Pour une fenêtre VS Code réellement « perso », il faut l'ouvrir avec code-ctx perso — c'est le --user-data-dir séparé qui isole les sessions d'auth.

git dans ankora, déjà bon, sans rien taper : ankora est sous F:\PROJECTS\Apps\, donc le includeIf s'applique.

Une asymétrie à connaître

gh et vercel savent utiliser un dossier de config dédié : tu fais gh auth login / vercel login une fois par contexte, et c'est réglé pour toujours, sans jeton à gérer.

supabase, lui, n'a aucun équivalent. Son seul point d'entrée est la variable SUPABASE_ACCESS_TOKEN. Pour Supabase — et seulement lui — tu es obligé de créer un jeton et de le mettre au coffre.

* C'est pour ça qu'un wrapper a été ajouté au module : il rend Supabase automatique par projet, y compris avec plusieurs comptes dans un même contexte. Voir section 9.

4 · Comment tu bosses, concrètement

Deux commandes couvrent 95 % des cas. Le reste, c'est du bon sens sur quelle fenêtre tu utilises.

La règle en une phrase

Une fenêtre VS Code par contexte, et work dans tout terminal que tu ouvres toi-même. Tes projets perso s'ouvrent tous dans la même fenêtre — il n'y a pas une fenêtre par projet.

Cas 1 — Je démarre ma journée sur un projet

work perso
code-ctx perso "F:\PROJECTS\Apps\ankora"

Le second argument est le projet que tu veux ouvrir. C'est la forme à privilégier : VS Code s'ouvre directement sur ankora, avec son package.json, son tsconfig, son node_modules — les extensions (ESLint, TypeScript, Tailwind) trouvent leur configuration là où elles l'attendent.

code-ctx perso    # sans chemin → ouvre toute la racine F:\PROJECTS\Apps

Sans chemin, tu obtiens l'arborescence complète de tes 17 projets dans l'explorateur. Pratique pour naviguer, moins bon pour travailler : les extensions raisonnent alors sur la racine et non sur le projet, ce qui les rend lentes ou muettes.

La bonne habitude

Un projet = code-ctx perso "<chemin du projet>". Tu peux en ouvrir plusieurs : ils apparaissent comme des fenêtres distinctes, mais partagent le même --user-data-dir, donc le même compte GitHub. Une identité, plusieurs fenêtres.

Cas 2 — J'ouvre un terminal dans VS Code

Le terminal intégré hérite du contexte si la fenêtre a été lancée à froid depuis un shell où work était passé. Sinon, non. Dans le doute, une seule commande :

ctx

GO → tu peux y aller. NO-GO → lis la ligne rouge, elle dit quoi faire. Le correctif est presque toujours :

work perso -NoCd     # -NoCd = reste dans le dossier courant

Cas 3 — Je vais pousser du code

Le seul réflexe qui compte vraiment :

ctx

Il croise trois choses d'un coup — le dossier, l'identité active, et le compte GitHub réellement authentifié. C'est le seul moyen d'attraper le scénario dangereux : être dans le dossier d'un contexte avec l'identité d'un autre.

Cas 4 — Je lance un agent IA (Claude Code, Cursor…)

Lance-le depuis un terminal où work est passé. L'agent hérite des variables d'environnement du terminal, donc des jetons du contexte — et uniquement de ceux-là. C'est ce qui le rend capable de travailler sans jamais avoir les secrets d'un autre client.

Claude Code connaît le dispositif — dans tous tes projets

Un protocole agent est chargé automatiquement à chaque session, quel que soit le projet ouvert : ~\.claude\CLAUDE.md importe ~\.claude\devcontext-agent.md.

Il lui demande de lancer ctx au démarrage et de rapporter le verdict, de refuser de pousser ou déployer sur un NO-GO, de connaître les pièges (URL avec login@, user.email en dur, index Supabase périmé) et de ne jamais écrire un jeton ailleurs que dans le coffre.

Pourquoi pas un fichier par projet : ankora et Terminal Learning sont des dépôts publics. Un CLAUDE.md par projet publierait tes chemins, emails et noms de comptes. Le fichier global ne part que dans claude-config, qui est privé.

Concrètement : demande « on est bien sur le bon compte ? » dans n'importe quel projet, il saura quoi vérifier et quoi te répondre.

Ce que tu ne fais plus jamais

  • Te déconnecter de GitHub pour passer d'un compte à l'autre
  • Faire gh auth switch
  • Te demander « sous quelle identité je viens de commiter ? » — git décide par le dossier
  • Ouvrir une fenêtre VS Code par projet — une par contexte suffit

Quelle fenêtre VS Code garder ?

La nouvelle, celle lancée par code-ctx. L'ancienne (lancée par l'icône du menu Démarrer) utilise la config globale de la machine — dont le compte gh, qui est celui du client. Elle n'est pas dangereuse pour tes commits (git décide par le chemin), mais Copilot, le panneau Source Control et ses terminaux y sont sur le compte global.

Correctif : rien à reconfigurer — ouvre le projet, pas la racine : code-ctx perso "F:\PROJECTS\Apps\ankora".

Et si je bosse sur mon autre portable ?

DevContext n'y est pas forcément installé. Deux repères :

  • ctx introuvable → le dispositif n'est pas là. Ni includeIf, ni clés dédiées : l'identité git est celle configurée globalement sur cette machine. Vérifie avec git config user.email avant de commiter.
  • Le protocole agent (ci-dessous) demande à Claude Code de le signaler explicitement au lieu de supposer.

6 · Nouveau projet perso

Rien à créer côté DevContext. Le contexte perso couvre toute la racine F:\PROJECTS\Apps\.

work perso                      # cd automatique sur F:\PROJECTS\Apps
mkdir mon-projet ; cd mon-projet

gh repo create thierryvm/mon-projet --private --source=. --remote=origin

La seule règle à ne pas casser

Le projet doit vivre sous F:\PROJECTS\Apps\. Ailleurs, le includeIf ne s'applique pas et tu commits sous l'identité git globale de la machine.

7 · Nouveau client pro — procédure éprouvée

Modèle : un Gmail dédié par client, transféré au client en fin de mission. La séquence ci-dessous est celle réellement exécutée pour client-a le 8 août 2026, corrections comprises. Compter 30 à 40 minutes, et ne pas la lancer entre deux rendez-vous.

Le principe qui rend l'opération sans risque

ctx-new active la réécriture d'URL immédiatement, alors que la clé n'est pas encore sur GitHub. Entre les deux, les git push de ce dépôt échouent. L'étape 3 supprime complètement cette fenêtre : on neutralise la règle juste après sa création, et on ne la réactive qu'une fois la clé vérifiée.

0 — Agent SSH — une seule fois par machine
Terminal administrateur · à sauter s'il tourne déjà

Sans agent, une clé protégée par phrase secrète la redemande à chaque push. Avec, tu la donnes une fois et c'est réglé, y compris après redémarrage.

Set-Service ssh-agent -StartupType Automatic
Start-Service ssh-agent
Get-Service ssh-agent   # attendu : Running / Automatic
1 — Ranger le code hors de Apps\
Deux contextes ne peuvent pas partager une racine — ctx-new refuse
F:\PROJECTS\Clients\<client>\

Si le dépôt a des worktrees, les déplacer ensemble puis git worktree repair. Et penser à l'historique Claude Code, indexé par chemin (voir section 11).

2 — Créer le contexte
Générer d'abord la phrase secrète dans KeePassXC, et l'y enregistrer
ctx-new <client> `
  -Label "Nom Client" `
  -Email "compte.client@gmail.com" `
  -Root "F:\PROJECTS\Clients\<client>" `
  -GithubLogin "login-github-du-client"

ssh-keygen demande la phrase secrète deux fois, en aveugle — rien ne s'affiche. Mets-en une : cette clé ouvre les dépôts d'un client, et les vers npm de 2026 ciblent précisément les clés SSH.

Puis 4 demandes de jetons → Entrée × 4. gh et vercel se branchent par navigateur, c'est plus propre qu'un jeton.

3 — Neutraliser la règle ← à faire tout de suite
Ramène la fenêtre de casse à zéro
Rename-Item 'F:\CTX\<client>\gitconfig' 'gitconfig.off'

Le includeIf pointe vers ce fichier ; absent, git l'ignore silencieusement. Tu retrouves exactement le comportement d'avant ctx-new. Vérifie-le :

git -C '<repo>' remote get-url --push origin   # doit rester en https://
git -C '<repo>' ls-remote --heads origin       # doit passer
4 — Clé SSH sur le compte GitHub du client
Chaque contexte a sa propre clé — c'est tout l'intérêt
Get-Content F:\CTX\<client>\ssh\id_ed25519.pub | Set-Clipboard
ssh-keygen -lf F:\CTX\<client>\ssh\id_ed25519.pub   # note l'empreinte

Connecte-toi à GitHub avec le compte du client — profil Chrome dédié ou navigation privée — puis Settings → SSH keys → New. Type = Authentication Key, jamais Signing Key.

Contrôle : l'empreinte affichée par GitHub après ajout doit correspondre à celle relevée ci-dessus. Si elle correspond à ta clé perso, tu t'es trompé de compte.

5 — Charger la clé et tester
ssh-add F:\CTX\<client>\ssh\id_ed25519   # phrase secrète, une fois pour toutes
ssh -T git@github-<client>

Point de bascule. Tant que la réponse n'est pas Hi <login-client>!, ne réactive rien.

6 — Réactiver, et pointer git vers le bon ssh.exe
Rename-Item 'F:\CTX\<client>\gitconfig.off' 'gitconfig'
git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"

La seconde ligne est indispensable dès qu'une clé porte une phrase secrète — voir l'encadré des deux ssh.exe en tête de guide. Sans elle : Permission denied (publickey) alors que ssh -T fonctionne.

git -C '<repo>' remote get-url --push origin   # git@github-<client>:…
git -C '<repo>' ls-remote --heads origin       # doit passer

Vérifie aussi un dépôt perso au passage : c'est le seul moment où une régression croisée est possible.

7 — Nettoyer l'URL du remote
Sans ça, la réécriture ne s'applique pas — voir section 8
git -C '<repo>' remote set-url origin https://github.com/<org>/<repo>.git

9 — La fenêtre VS Code du client
work <client>
code-ctx <client> "F:\PROJECTS\Clients\<client>\<repo>"

Elle s'ouvre vierge : 0 extension, pas de réglages. Deux connexions, et ce sont deux comptes différents :

Pour le second : Ctrl+Shift+P → Settings Sync: Turn On → « Sign in with another account ». VS Code proposera le compte client par défaut : ne le prends pas, son cloud est vide.

La connexion GitHub rouvre la mauvaise fenêtre

Le retour du navigateur passe par une URL vscode://, protocole enregistré au niveau de l'installation et non de la fenêtre : il réveille l'instance par défaut. Ferme les autres fenêtres avant, ou utilise le lien « Having trouble? » de la page GitHub, qui donne un code à coller directement.

Ce n'est pas bloquant : git commit, push et le panneau Source Control fonctionnent sans cette connexion — ils passent par la clé SSH. Seuls Copilot et les onglets PR/Issues en dépendent.

8 · Le piège des URL de remote

La réécriture insteadOf est un préfixe de chaîne, pas une compréhension d'URL. Une URL qui contient un nom d'utilisateur ne matche pas :

URL du remoteAprès réécriture
https://github.com/org/repo.gitgit@github-<ctx>:org/repo.git ✓
git@github.com:org/repo.gitgit@github-<ctx>:org/repo.git ✓
https://login@github.com/org/repo.gitinchangée ✗

Une URL non réécrite part en HTTPS via le credential helper, donc sur le compte gh global — le dernier connecté. C'est exactement la panne que le dispositif existe pour empêcher.

Le réflexe, sur tout dépôt nouveau ou cloné 
git remote get-url --push origin

Si la réponse ne commence pas par git@github-<ctx>:, corrige avec remote set-url en retirant le login@.

9 · Plusieurs comptes Supabase dans un même contexte

DevContext ne prévoyait qu'un supabase-token par contexte. Un wrapper a été ajouté au module le 8 août 2026 pour lever cette limite : c'est le dossier du projet qui choisit le compte, comme le includeIf le fait déjà pour l'identité git.

Tu ne tapes rien de plus

Exactement les mêmes commandes qu'avant. Le wrapper est invisible : il se contente de charger le bon jeton avant de passer la main à la vraie CLI.

Comment il décide

  1. Il remonte l'arborescence depuis le dossier courant à la recherche de supabase\.temp\project-ref — un fichier que la CLI Supabase écrit elle-même au moment du supabase link.
  2. Il consulte l'index F:\CTX\<ctx>\supabase-index.json, qui associe chaque project-ref à une clé du coffre.
  3. Il charge ce jeton le temps de la commande, puis restaure l'état précédent.

Hors contexte, ou dans un dossier sans projet lié, il ne décide rien et laisse passer ce que work a déjà posé. Un wrapper qui devine serait pire que pas de wrapper.

Correctif du 8 août 2026 — le wrapper ne suffisait pas

Le wrapper n'intercepte que les commandes tapées dans PowerShell. Un binaire appelé directement — execFileSync depuis Node, un script bash, un agent IA — ne le traverse jamais : il ne voit que la variable SUPABASE_ACCESS_TOKEN, que work figeait sur le compte par défaut.

Résultat : le préflight d'Ankora listait trois projets sans jamais voir ankora-prod. La commande réussissait, sur le mauvais compte — pire qu'une panne, parce qu'invisible.

Corrigé à la racine : work résout maintenant le jeton d'après le dossier, et un hook le resynchronise à chaque cd. $env:DEVCTX_SUPABASE_KEY dit quelle clé est active, et ctx rend NO-GO si elle ne correspond pas au projet.

Ce que tu vois

PS F:\PROJECTS\Apps\ankora> supabase projects list
  [ankora-prod -> supabase-token-2]     ← bascule signalée
  ankora-prod

PS F:\PROJECTS\Apps\airsoft-aywaille> supabase projects list
  Terminal Learning                     ← compte par défaut, aucun message
  IronTrack
  airsoft-aywaille

Le message n'apparaît que lorsque le compte utilisé n'est pas celui chargé par work. Signaler l'exception, pas la normale.

Reconstruire l'index — sb-index

L'index se construit tout seul en listant les projets de chaque jeton du coffre. Aucune table à tenir à la main.

work perso
sb-index

Quand le relancer : après avoir créé un projet Supabase, après un supabase link sur un nouveau dépôt, ou après avoir ajouté un compte. Si tu oublies, le wrapper te le dit : Projet 'xxx' absent de l'index Supabase. Lance 'sb-index'.

Ajouter un troisième compte

$t = Read-Host "PAT compte n°3" -AsSecureString
Set-Secret -Vault DevContext -Name "devctx/perso/supabase-token-3" -SecureStringSecret $t
Remove-Variable t
sb-index

N'importe quelle clé commençant par supabase-token est ramassée automatiquement. Seule supabase-token (sans suffixe) est le compte « par défaut », celui que work charge et que le wrapper n'annonce pas.

Le login Supabase global a été supprimé

supabase logout a été exécuté le 8 août 2026. Conséquence voulue : hors contexte, la CLI répond Access token not provided au lieu de partir silencieusement sur un compte non choisi. Si tu vois cette erreur, la réponse est work <contexte>.

Ce que le wrapper ne couvre pas

L'application qui tourne (URL, anon key, service_role) se connecte via le .env.local de chaque projet — déjà isolé par dossier, sans rapport avec le wrapper. Le wrapper ne concerne que la CLI : link, db push, functions deploy, projects list, migration…

10 · Fin de mission

ctx-end <client>            # affiche la checklist de transfert
ctx-off                     # obligatoire : on ne purge pas sous soi
ctx-end <client> -Purge      # + supprime secrets et dossier de contexte

La checklist couvre ce qui casse un transfert de comptes : 2FA encore liée à ton téléphone, moyen de paiement personnel, email de récupération, tokens non révoqués.

Supprimer un token du coffre ne le révoque pas

Il faut aller le révoquer chez le fournisseur. ctx-end rappelle les URL.

12 · Ce qui n'est pas protégé

  • Ce n'est pas une frontière cryptographique. DPAPI est scopé à ton compte Windows : les bases restent déchiffrables par le même utilisateur. Contre le mélange de comptes, efficace. Contre un attaquant local, non — il faudrait des comptes Windows séparés ou des VM.
  • Les jetons vivent en variables d'environnement. Tout processus enfant du terminal en hérite, y compris un agent IA. C'est ce qui le rend capable de travailler, et ce qui fait qu'il n'a jamais les secrets d'un autre contexte. À connaître avant de lancer un agent.
  • Un dépôt hors des racines déclarées n'est couvert par rien. Ni includeIf, ni insteadOf. ctx le signale : « hors de la racine du contexte actif ».
  • Un user.email local dans .git/config court-circuite le garde-fou — il prime sur le includeIf. Utile à savoir quand une valeur semble « bonne » sans que le mécanisme y soit pour quelque chose.
